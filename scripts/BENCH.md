# Бенчмарк swap / zswap

`scripts/bench.sh` сравнивает конфигурации swap и zswap под нагрузкой
нехватки памяти. По его результатам выбираются значения по умолчанию
в профилях RamPlus (см. правила в `CLAUDE.md`).

> **Цифры из VM нерепрезентативны.** Диск виртуальной машины кэшируется
> в RAM хоста, поэтому swap в VM выглядит намного быстрее, чем на реальном
> диске, а соотношение «swap против zswap» искажается. В VM бенчмарк
> годится только для проверки, что скрипт работает. Для выводов и для
> выбора значений по умолчанию нужен запуск на реальном SSD (лучше на
> двух-трёх разных машинах). В `summary.md` прогона в VM это
> предупреждение добавляется автоматически.

## Что меняет скрипт

Бенчмарк **меняет систему**: отключает весь swap (включая zram), меняет
параметры zswap, создаёт временный `/ramplus-bench.swapfile`. При выходе
(в том числе по Ctrl+C или при ошибке) исходное состояние возвращается:
swap включается с прежними приоритетами, параметры zswap восстанавливаются,
временный файл удаляется. Поэтому скрипт запускается только с явным
согласием:

```sh
make build-probe
sudo RAMPLUS_VM_TEST=1 scripts/bench.sh                # в одноразовой VM
sudo scripts/bench.sh --i-know-this-changes-swap       # на реальной машине
```

Перед запуском закройте всё важное: при нагрузке без swap OOM killer может
убить случайный процесс.

Зависимости: `stress-ng` (для нагрузки `hot`), бинарник `ramplus-probe`.

## Конфигурации

| имя | что включено |
|---|---|
| `no-swap` | swap выключен (ожидаемо — отказ при нагрузке больше RAM) |
| `swap` | swapfile `--swap-size` (4G) на корневой ФС |
| `zswap-lz4` | swap + zswap, lz4, zsmalloc |
| `zswap-zstd` | swap + zswap, zstd, zsmalloc |
| `zswap-lzo-zbud` | swap + zswap, lzo, zbud (по умолчанию в Ubuntu) |

Если конфигурация недоступна на этом ядре (например, в новых ядрах нет
zbud, а в некоторых не собран нужный компрессор), прогон помечается
`skipped` с причиной.

Перед каждым прогоном состояние сбрасывается: весь swap выключается,
zswap выключается, выполняются `drop_caches` и пауза (`--pause`, 10 с).

## Нагрузки

| имя | что делает |
|---|---|
| `hot` | `stress-ng --vm 1 --vm-bytes N --vm-keep`: все страницы постоянно активны. Худший случай для swap и zswap. Данные — собственный шаблон stress-ng |
| `hot-probe` | `ramplus-probe workload --hot 1.0`: то же, но с управляемым типом данных |
| `cold` | `ramplus-probe workload --hot 0.15`: выделить N, заполнить, затем работать только с 15% памяти. Реалистичный десктоп: много фоновой, редко нужной памяти |

Типы данных для `hot-probe` и `cold` (`--data`):
- `compressible` — примерно 3:1, как типичная память процессов. Треть
  страницы случайная, остальное — повторяющийся шаблон. Одинаково
  заполненных страниц нет: zswap хранит такие отдельно, и это исказило бы
  результат;
- `random` — случайные несжимаемые данные. Худший случай для zswap.

Объём нагрузки по умолчанию — 1.3 × RAM (`--work-size`).

## Что измеряется

Параллельно с нагрузкой работают:
- `ramplus-probe sample` — раз в 200 мс читает `/proc/meminfo` и
  `/proc/pressure/memory` (`samples.csv` в каталоге прогона);
- `ramplus-probe latency` — маленький «интерактивный» процесс. Каждые
  100 мс он трогает 50 MiB своей памяти и записывает задержку (p50, p99,
  max). Показывает, насколько тормозит отзывчивость, пока идёт нагрузка.

Каждая комбинация прогоняется 3 раза (`--runs`), в сводке — медиана по
успешным прогонам.

## Результаты

```
bench-results-<время>/
  env.json            ядро, виртуализация, RAM, параметры запуска
  results.csv         одна строка на прогон
  summary.md          сводка: медианы по конфигурациям
  runs/<config>__<workload>__<data>__<N>/
    meta.json         статус (ok | failed | oom | timeout | skipped), длительность
    samples.csv       замеры meminfo/PSI
    sample.json       пики и средние
    latency.json      p50/p99/max latency-probe
    workload.json     итог нагрузки ramplus-probe
    workload.log      вывод нагрузки
```

Колонки сводки:
- успех — сколько прогонов из N завершились;
- длительность;
- пик занятого swap и пик пула zswap;
- PSI some и full: пик avg10 и среднее за прогон (по счётчику `total`);
- latency p50 и p99;
- скорость обхода горячих страниц. Абсолютное значение условно, его
  нужно сравнивать между конфигурациями.

Пересобрать отчёт по готовому каталогу: `ramplus-probe report <каталог>`.

## Полный прогон и быстрый

Полный прогон по умолчанию: 5 конфигураций × 5 вариантов нагрузки × 3
прогона по 30 с плюс паузы — примерно 1–1,5 часа. Проверить, что всё
работает: `--quick` (1 прогон, 15 с). Сузить набор можно через `--configs`,
`--workloads` и `--data`.
